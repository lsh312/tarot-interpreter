**Live app:** https://tarot-interpreter.vercel.app

## 1. Overview

Tarot Interpreter is a full-stack AI application that generates personalised tarot readings using Retrieval-Augmented Generation (RAG). A user selects a spread, optionally asks a question, and receives a reading in which real cards are drawn from a shuffled deck, their symbolic meanings retrieved from a vector database, and a contextual interpretation generated by Claude.

The project demonstrates end-to-end applied AI engineering: data ingestion, vector search, LLM integration with prompt caching, a REST API, and a production-deployed React frontend.

---

## 2. System Architecture

```
Browser (React/Vite)
        │
        │  HTTPS POST /reading/*
        ▼
FastAPI (Render, Docker)
        │
        ├── TarotAgent.draw()         → random card selection
        ├── Chroma vector DB          → retrieve card meanings via semantic search
        └── Anthropic API (Claude)    → generate interpretation
                                         with system prompt caching
```

The backend is stateless at the request level — all mutable state (the shuffled deck draw, the question) is scoped to a single request. The `TarotAgent` instance is initialised once at startup via FastAPI's lifespan context and shared across all requests, avoiding repeated model loading.

## 3. Data Pipeline — RAG Ingest

### 3.1 Source Data

The dataset is a handcrafted JSON file of all 78 tarot cards (`data/tarot_cards.json`). Each card entry contains:

- `name`, `arcana` (Major/Minor), `suit` (for Minor Arcana)
- `keywords` — a short list of thematic words
- `upright_meaning`, `reversed_meaning` — full prose meanings
- `symbolism` — iconographic description
- `element`, `astrological` — esoteric correspondences
- `image_filename` — path to the card image served statically

### 3.2 Embedding and Indexing

The ingest script (`src/ingest.py`) converts each card into a LangChain `Document`. The page content concatenates all textual fields into a single structured string so that the embedding captures the full semantic richness of the card:

```
Card: The Moon
Arcana: Major | Suit: N/A
Element: Water
Astrological: Pisces
Keywords: confusion, fear, illusion, subconscious, dreams
Upright: ...
Reversed: ...
Symbolism: ...
```

Documents are embedded using `sentence-transformers/all-MiniLM-L6-v2` (a 384-dimension model running locally on CPU) and stored in a Chroma vector database persisted to `models/chroma_db/`. The ingest step runs once at Docker build time, so the vector store is baked into the container image and available immediately at startup — no cold-ingest delay on Render.

**Why a local embedding model?** Anthropic does not offer an embeddings API. Using a local HuggingFace model avoids introducing a second API provider and keeps the ingest step free and deterministic.

**Why Chroma?** The corpus is small (78 documents, static). Chroma persists to disk with zero infrastructure overhead. Swapping to Pinecone or another managed vector DB would only require updating `config.yaml` and a thin adapter — the ingest and retrieval interfaces are provider-agnostic.

## 4. TarotAgent

`TarotAgent` (`src/agents/tarot_agent.py`) is the core orchestration class. It handles card drawing, context formatting, and LLM calls for all three spread types.

### 4.1 Card Drawing

Cards are drawn using `random.sample` (without replacement) from the full 78-card deck, with each card assigned a random orientation (`is_reversed = random.random() < 0.5`). This ensures:

- No duplicate cards within a single reading
- Roughly 50% reversed probability, matching real-world shuffling

### 4.2 Context Formatting

Each drawn card is formatted into a structured block passed to the LLM:

```
**Past: The Moon** (Reversed)
Keywords: confusion, fear, illusion
Meaning: When reversed, The Moon suggests...
Symbolism: A moon over a still pool...
```

This gives Claude all the symbolic context it needs to generate a grounded, specific interpretation rather than a generic one.

### 4.3 LLM Integration

Claude Haiku (`claude-haiku-4-5-20251001`) is used for all readings. The API call uses the streaming client (`client.messages.stream`) and collects the final message — this keeps the implementation simple while leaving the door open to true streaming to the frontend in a future iteration.

**Prompt caching** is applied to the system prompt using Anthropic's `cache_control: ephemeral` flag. Since the system prompt is identical for every request, it is stored server-side for up to 5 minutes after the first call. This reduces both latency and token cost on repeated calls — particularly relevant on the free Render tier where traffic bursts can occur after cold starts.

**Why sync route handlers?** The Anthropic SDK's streaming client is synchronous. FastAPI runs synchronous handlers in a thread pool automatically, making sync the correct choice here — using `async def` with a blocking synchronous call would stall the event loop.

### 4.4 Spread Types

| Spread | Cards | Prompt target |
|---|---|---|
| Daily Card | 1 | 150–200 words — energy and guidance for the day |
| Three Card | 3 | 250–300 words — past/present/future narrative |
| Celtic Cross | 10 | 400–500 words — detailed positional reading |

Each spread has its own prompt template that instructs Claude on length, structure, and how to weave the positional cards into a cohesive answer to the user's question.

## 5. API Design

The FastAPI layer (`src/api/`) exposes four endpoints:

| Method | Path | Description |
|---|---|---|
| `GET` | `/health` | Liveness check |
| `POST` | `/reading/daily` | Draw 1 card, no question |
| `POST` | `/reading/three-card` | Draw 3 cards with question |
| `POST` | `/reading/celtic-cross` | Draw 10 cards with question |
| `GET` | `/images/{filename}` | Serve card images as static files |

All reading endpoints return the same response shape:

```json
{
  "spread_type": "three_card",
  "question": "Should I take the new role?",
  "cards": [
    {
      "position": "Past",
      "name": "The Tower",
      "orientation": "Upright",
      "keywords": ["upheaval", "revelation", "sudden change"],
      "meaning": "...",
      "image_filename": "major_16.jpg"
    }
  ],
  "interpretation": "..."
}
```

The `TarotAgent` singleton is attached to `app.state` during the FastAPI lifespan context, injected into route handlers via `request.app.state.agent`. This avoids re-instantiating the agent (and reloading config/card data) on every request.

CORS origins are driven by `config.yaml`, making it easy to add new allowed origins (e.g. a new deployment URL) without touching application code.

## 6. Frontend

The frontend (`frontend/`) is a React 18 / Vite single-page application styled with Tailwind CSS and animated with Framer Motion.

### 6.1 State Machine

The UI is organised as a simple screen state machine in `App.jsx`:

```
select → question → loading → reading
  ↑                               │
  └───────────── reset ───────────┘
```

The `daily` spread skips the `question` screen and goes directly to `loading`.

### 6.2 Components

| Component | Responsibility |
|---|---|
| `SpreadSelector` | Grid of three spread options with editorial card layout |
| `QuestionInput` | Textarea for user question with spread-specific label |
| `TarotCard` | Individual card with CSS 3D flip animation; auto-reveals on a staggered timer |
| `ReadingView` | Orchestrates card reveal sequence; shows interpretation once all cards are revealed |
| `Interpreter` | Typewriter effect for the AI-generated interpretation text; parses markdown headings and bold formatting |
| `Background` | Fixed decorative layer with mystical illustration assets at low opacity |

### 6.3 Card Reveal Sequence

Cards flip automatically using a staggered timer (`index * 600ms + 400ms`), creating a cinematic reveal. Each card reports back to `ReadingView` via `onRevealed()`. Once all cards have reported, the interpretation appears — ensuring the user reads the cards before the text.

### 6.4 Markdown Rendering

Claude's interpretation responses contain markdown formatting (headings, bold text). The `Interpreter` component strips heading markers and renders `**bold**` spans inline without a third-party markdown library, keeping the bundle lean.

|---|---|

Tests are run in CI via GitHub Actions on every push to `main`.

## 8. Deployment

| Layer | Platform | Method |
|---|---|---|
| Frontend | Vercel | Automatic deploy from GitHub (`frontend/` root) |
| Backend | Render | Docker (auto-deploy from GitHub `main`) |

The Dockerfile builds a `python:3.11-slim` image, installs dependencies, runs the ingest step to bake the Chroma vector store into the image, and starts Uvicorn on port 8000:

```dockerfile
FROM python:3.11-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
RUN python -m src.ingest
EXPOSE 8000
CMD ["uvicorn", "src.api.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

Running ingest at build time means the vector store is ready at container startup — there is no first-request ingest delay. The `ANTHROPIC_API_KEY` is injected as a Render environment variable and never committed to the repository.

**Cold start behaviour:** Render's free tier spins down idle services. The first request after an idle period takes ~30 seconds while the container restarts. Subsequent requests are fast.

## 9. Cost and Performance

| Factor | Detail |
|---|---|
| LLM model | Claude Haiku — the most cost-efficient Claude model |
| Prompt caching | System prompt cached for 5 minutes; cache hits reduce input token cost by ~90% |
| Embeddings | Local model — zero ongoing cost |
| Vector DB | Chroma on disk — zero ongoing cost |
| Hosting | Render free tier (backend) + Vercel free tier (frontend) |

Estimated cost per reading at standard Haiku pricing: **< $0.001** per request.

## 10. Design Decisions Summary

| Decision | Rationale |
|---|---|
| RAG over pure prompting | Grounding Claude in structured card meanings produces more accurate, symbolically faithful interpretations than asking Claude to recall tarot knowledge from training data |
| Local embeddings | No second API provider; ingest is free and reproducible |
| Chroma over managed vector DB | Corpus is static and small; disk persistence is sufficient |
| Sync route handlers | Anthropic streaming SDK is synchronous; async handlers would block the event loop |
| Prompt caching | Identical system prompt across all requests makes caching a free latency and cost win |
| Baked vector store in Docker | Eliminates cold-ingest delay on container startup |
| Config-driven CORS and spreads | Adding a new deployment or spread type requires only a `config.yaml` change |

## 11. Potential Extensions

- **Streaming responses** — pipe Claude's streaming output directly to the frontend via Server-Sent Events for a live typewriter effect without buffering the full response
- **User accounts** — persist reading history per user with a lightweight database
- **Spread customisation** — allow users to define their own positional spreads via the UI
- **Richer retrieval** — filter vector search by arcana or suit to surface more targeted card meanings
- **Image generation** — use a generative model to create unique card imagery per reading
